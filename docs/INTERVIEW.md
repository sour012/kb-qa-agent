# 面试追问与答法

按「先给结论 → 再给数字/代码位置 → 最后说局限」的顺序答，别背定义。

---

### 1. 你的 RAG 和「文档塞进 prompt」有什么区别？

关键在于**检索是有判断的**，不是无脑拼接。三个判断：切分保证一条规则不被截断、混合检索 + 重排保证取到一个对的块、覆盖率判据保证「取不到就不答」。把整篇文档塞进 prompt 在 9 篇语料上也能跑，但它没有可度量、可回归的边界——文档变成 900 篇时，它第一个崩。

### 2. 为什么用 BM25 + 向量的混合，不做纯向量？

制度/技术文档里大量精确标识：条款号、金额、时限、「第 3 条」。BM25 对这些极其敏感，向量反而会把「第 12 条」和「第 21 条」判成相似。反过来「出差补贴」和「差旅补助」这种同义改写，BM25 直接漏。两路互补，融合用 RRF，因为它不需要处理两路分数不同量纲的问题。

### 3. RRF 的 k 取 60 是什么依据？调过吗？

60 是 Elasticsearch/Vespa 的经验默认值，作用是把 1/(k+rank) 压得足够平缓，避免「第一名碾压后面」。我试过 10 和 200：k 小的时候，单路排名靠前的结果几乎垄断输出；k 大的时候两路融合过于平均，精确匹配的优势消失。60 在自建评测集上 recall@5 与 MRR 都最稳，但这是 27 条样本的结论，样本量不足以支撑强结论——我会说「按经验值起步，用回归测试守住不退化」。

### 4. 你怎么判断「知识库没有，应该拒答」？

用**字符 bigram 覆盖率**：问题原文的字符二元组有多大比例出现在 top1 块里。低于 14% 拒答。为什么不用融合分：RRF 归一化后第一名恒为 1.0，库里没内容时也是 1.0，天然无法表达绝对相关性。为什么不用 IDF 词覆盖率：分词粒度会骗人——「多久」「之内」这类词在库里 df=0，IDF 极高，把可回答的问题压到 0.13，而无意义问题拿到 0.195，两类直接颠倒。字符级绕开分词，量纲也绝对。

（面试官如果追问：这个阈值的样本量多大？——27 条，两类只差 0.03，属于小样本标定，换语料必须重标；生产上更该训 no-answer 判别器。）

### 5. 为什么要「查询扩展」，什么时候触发？

只在覆盖率低于 28% 时触发一次，加两类词：领域同义词（报销→差旅/费用/发票）和 top1 块里的高 IDF 词。无条件下扩词会把「住宿能报多少」扩成「住宿 差旅 费用 发票」，主题被稀释，反而更差——这个坑我踩过，第一版就是无条件扩词，答案质量明显下降。

另一个坑：**扩展之后不能拿扩展后的词去算覆盖率做拒答判断**，那等于自己给自己抬分。必须用用户原话重新算。

### 6. 抽取式回答听起来很弱，为什么默认不开 LLM？

因为**生成模型不是 RAG 的必要条件**。检索质量决定了上限，LLM 只决定表达是否通顺。默认抽取式带来三个好处：离线可跑、零成本、答案句句可溯源（没有幻觉空间）。真正需要跨段归纳时才开 LLM：`llm.enabled: true` + `DEEPSEEK_API_KEY`，走 OpenAI 兼容接口，链路其余部分不变。

开 LLM 时风险换了个位置：不再是「答不出」，而是「答得顺但数字错」。所以自检层对两种模式都在跑。

### 7. 你说的「引用自检」具体怎么算？

把答案按句切，去掉 `[n]`，算这句话的字符 bigram 有多大比例出现在它引用的原文块里（containment，不是 Jaccard，因为短句对长文）。低于 0.34 判依据不足，全篇平均低于阈值就降级成「依据较弱，请核对原文」。改一个数字要能被检出来——单测里有一条就是「一线城市 900 元」的支持度必须掉到 1.0 以下。

踩过的坑：模型和模板都把引用标在句号后面（`……600 元。[1]`），按句号硬切会把 `[1]` 切给下一句，导致所有句子被误判为「无引用」，支持度直接掉到 2%。现在会把句首的引用标记并回上一句。

### 8. 切分参数 460 / 120 / 80 怎么定的？

压测 + 语料特性。制度类文档一个小节通常 300~500 字，460 能让大多数小节完整落在一块；低于 200 字会切出大量「半句块」，重排也救不回来；超过 800 字向量被稀释，且送进 LLM 后中间段落注意力衰减。重叠取 80 字且按整句回退——字符级重叠会在句中断开，制造新的假边界。尾块低于 120 字并回上一块，避免「一句话块」靠巧合拿高分。

### 9. 这套东西上线要改什么？

四件事：索引从 pickle 换成 ES/向量库并支持增量更新（现在是全量重建，27 块 0.3 秒，万级块不行）；会话记忆从进程内字典换 Redis 带 TTL；文档解析补表格（现在是纯文本层，表格退化成一行行字）和多格式（Excel、HTML）；评测集换成真实用户日志 + 人工标注，并把四项指标接进 CI，指标退化直接卡发布。

### 10. 这个项目最大的不足是什么？

**评测太容易。** 语料只有 9 篇、27 块，题目是从文档反推的，措辞和原文高度重合，所以 recall 100%、MRR 1.0——这个数字不能作为能力证明，只能当回归测试用。真实语料上（几百上千篇、有同义改写、有版本冲突、有表格）同一套代码大概在 70%~85% 的 recall@5 区间，而且拒答阈值必须重新标定。

第二个不足是单跳检索：需要跨文档聚合的问题（「今年一共批了多少笔报销」）它做不了，那该走结构化查询，不是检索。我把这条写进 README 的「已知局限」了，而不是假装它能做。
